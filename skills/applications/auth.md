# Authentication, registration and resumable handoffs

Read current host/browser instructions first. Standing permission enables necessary ordinary account/session actions only within the tool's allowed scope. A helper must never be triggered to bypass a tool-required credential, CAPTCHA or binding-agreement confirmation.

Prefer an existing authorized account/session or official guest path; check the private site/account journal before creating duplicates. Verify expected account/client identity. Registration may be completed where authorized and supported; the person must complete any concrete required secret/confirmation action. Unknown factual registration fields follow the answer-bank workflow.

Use secret references rather than secret values in agent-visible records. A private owner-readable local file outside source is a minimal option; an existing password manager is preferable. Do not print passwords, one-time codes, tokens, cookies or secret-bearing links into tool output, chat, application journals or feedback. Do not send those to Telegram. Human secret entry is required when the adapter cannot safely consume a handle without exposing the value.

For a blocker save: canonical URL without secret query, portal/profile/session/capability scope, exact observed step/error, completed form sections, actual attachment state, timestamp, expiry/recheck condition, remaining action, responsible person and resume point. Record whether observed or inherited. One failure does not establish portal-wide failure. Reuse a shared portal blocker only within its evidence scope; invalidate it when the session is restored or a normal operation disproves it.

Explain the source of a mandatory handoff, group affected applications and continue independent work. After completion verify the session/action and resume from the checkpoint. Never equate an approval with actual completed registration/submission, and never close a suitable opportunity solely because it needs login.
